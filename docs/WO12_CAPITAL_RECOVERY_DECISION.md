# WO12 Capital Recovery Decision

**Decision: ADVANCE the compact permanent CLOSED successor as an experimental v2 architecture.** It recovered 466 CKB of owner-controlled untyped capacity from a 600 CKB Q policy Cell on an isolated CKB 0.210.0 node. The transaction paid a separate 2,000-shannon fee, retained a 134 CKB terminal Cell, and preserved an owner-only path for a fund created after closure. This is a local synthetic-token result, not production qualification.

The higher-ceiling direction is an independently versioned fund lock with a time-gated, owner-only recovery branch and a retirement-capable policy. It could return the remaining 134 CKB, but requires new F code, a fixed recovery epoch committed at treasury creation, and a larger F Script args footprint. WO12 did not implement it because its lifecycle and late-deposit rules need a separate security experiment.

## Baseline

The unchanged v1 Q state is 466 bytes. Its policy Cell contains 600 CKB; the measured occupied minimum is 572 CKB. On close, v1 requires the same-capacity successor, leaving all 600 CKB locked, including 28 CKB of slack. Its F input-type proxy Script commits to the full v1 Q Script hash and requires the policy input when protected funds are spent. Removing Q therefore strands current and future F cells. Owner close/sweep and a supported late sweep are recorded in WO10 evidence, but no v1 policy capacity is returned.

The v2 experiment keeps the 466-byte ACTIVE state and contracts only on an owner-authorized CLOSE to a 28-byte `QCT2` terminal record. That record keeps the canonical owner K lock args (20 bytes), closed marker/version and no delegate data. It remains under the same v2 Type ID and exact Q Script identity, cannot reopen, and is preserved at the same capacity on every sweep.

Identity was checked independently: the selected v2 policy uses Q data hash `0xc224bed30f3b40e9a1c14640ea503d95aab00700364d1237e5e16bc8cda5e04f`, `data2`, and a fresh 32-byte Type ID argument. Its full Q Script hash is `0x21a2342e424d734f2b10e5daff05c0ebe5c6ca5eda179d3f1ed9ea356130a1f4`; the selected fund input's generic proxy lock has exactly that value in its args. V1's Q data hash is `0x4c02a05d3ec9723f742dbc1323efef3e094995f9e5ecb043243239d712a4d876`. Matching or copying only a Type ID argument cannot make the different code hashes and full Scripts compatible.

## Capacity Result

| Policy lifecycle | State bytes | Policy capacity held | Occupied minimum | Returned to owner as untyped CKB | Policy capacity still locked |
| --- | ---: | ---: | ---: | ---: | ---: |
| v1 ACTIVE or CLOSED | 466 | 600 CKB | 572 CKB | 0 CKB | 600 CKB |
| v2 ACTIVE | 466 | 600 CKB | 572 CKB | 0 CKB | 600 CKB |
| v2 after CLOSE | 28 | 134 CKB | 134 CKB | 466 CKB | 134 CKB |

Node evidence accepted the 134 CKB output at the measured occupied minimum. The close transaction returned 46,600,000,000 shannons (466 CKB) of policy capacity to an untyped owner K output. It paid its 2,000-shannon fee from a separate owner fee Cell. The remaining 134 CKB is a permanent cost of retaining the owner-authenticated policy identity and late-sweep gate. It is not returned typed capacity.

The protected xUDT Cell remained at 154 CKB and owner xUDT outputs also retained typed-cell capacity. Those capacities are not counted as freely spendable CKB. Fees on the authorized spend, close, late deposit and sweep were each 2,000 shannons, paid from actor/owner untyped inputs. The isolated setup separately deployed a 24,328-byte Qv2 executable (24,389 CKB deployment output at `bytes + 61`); the dependency is reusable across treasuries if shared, but is a substantial one-time deployment cost if duplicated. It is not charged against the 466 CKB per-policy recovery result.

## Alternatives

| Design | Capital and owner recovery | Late deposits and early bypass | Identity, cost and compatibility | Assessment |
| --- | --- | --- | --- | --- |
| Compact permanent CLOSED successor (implemented) | Measured: 600 to 134 CKB policy capacity; owner receives 466 CKB untyped. 134 CKB remains permanently occupied. | Owner K must close and sweeps remain available forever. F still requires the exact Qv2 identity; delegates cannot spend after close. No timer or permissionless exit. | New Q binary, data hash and ABI; fresh Q Type ID. Existing generic F code can be instantiated with the new Q Script hash, but existing v1 fund args cannot be rewritten in place. One Q input still serializes delegated spends. | Strongest verified near-term compromise; meaningful, not complete, recovery. |
| Independent owner recovery in a new F lock | Could potentially allow Q deletion, but a lock needs durable, authentic proof that delegated authority has ended. An explicit terminal anchor has at least the same 134 CKB occupied policy footprint if it must remain for late deposits. Putting only an owner key in each F lock does not prove closure. | An owner branch usable while ACTIVE would bypass Q. A missing Q input is not proof of close. New F cells created after retirement must still know how the fallback applies. | Requires reviewed Fv2 contract, new lock Script identity and rewrapping; args/state add capacity per protected cell. More contract code and larger attack surface. Existing F/Q identity is incompatible. | Not better than the compact tombstone without a separately proven retirement signal. |
| Time-gated Fv2 recovery and Q retirement | Theoretical: after its fixed threshold, Fv2 permits owner-only recovery without Q and Q can potentially be deleted, returning its remaining 134 CKB. Policy recovery could rise from 466 to the full 600 CKB. The lock-args overhead is not yet measured in a node transaction. | A global absolute block threshold committed at treasury creation makes F cells deposited after the threshold recoverable immediately by the owner, even if deposited after Q retirement. Before the threshold, missing Q must reject. Only the owner can take the fallback; delegates still require Q. A lost owner key still strands funds. | Requires immutable Fv2 code and args binding full Q Script identity, owner K args and an absolute threshold (at least 28 extra args bytes in the straightforward encoding, hence at least 28 CKB extra occupied capacity per F cell). Needs a new deployment, explicit owner close then retire, and compatibility checks. | Highest ceiling, but must test since encoding, branch selection, reorg behavior, late deposits and per-fund capacity before choosing. |

The timed design is inspired by, not copied from, CrowdCell. Its [pledge lock](https://github.com/alesfer001/CrowdCell/blob/main/contracts/pledge-lock/src/main.rs) uses an absolute block `since` at an immutable campaign deadline; missing campaign state enables refund only after deadline plus 1,944,000 blocks. The [campaign type script](https://github.com/alesfer001/CrowdCell/blob/main/contracts/campaign/src/main.rs) delays retirement of either terminal status until that same grace has elapsed and blocks destruction in a transaction spending a pledge. Thus pledge-level recovery survives campaign-cell retirement. Its time period and backer-specific refund rule do not transfer directly to an owner-controlled spending treasury. QuotaCell's higher-ceiling experiment should use an owner-only fallback, a treasury-specific fixed threshold, and tests for deposits created after retirement.

The simplest independently-versioned F recovery branch with no timer but a “Q absent” condition is unsafe: Q absence can be caused by deletion before a valid terminal transition. A separate terminal anchor removes that ambiguity but keeps durable capacity. A timer can remove the anchor only if the fund lock itself knows the immutable threshold and can recover every later F cell.

## Node Implementation and Results

The v2 implementation in `policy/c/allowance_v2.c` and its isolated runner exercise on a fresh loopback-only, P2P-disabled dev node:

- Owner creates a fresh Qv2 Type ID policy, funds a fresh F Script whose args equal the full Qv2 Script hash, and Alice signs a 10-token payment.
- Ben's 51-token payment fails native Q validation with error 18 (per-payment ceiling).
- A close with a substituted terminal owner fails error 10; a forged `SWEEP`-style ACTIVE-to-terminal transition fails error 25.
- The correct owner CLOSE commits. The resulting 28-byte/134 CKB successor has a new outpoint and permanent v2 identity.
- After close, a new 50-token F cell is created from the owner's xUDT inventory. Alice cannot spend it (error 15); the owner sweeps it and the same terminal Q state commits again.
- Owner re-enable after close fails error 25. Terminal deletion fails error 11.

The exact transaction hashes, signed bytes, node replies, capacities, cycle measurements and selected live-cell snapshots are in [`evidence/wo12-capital-recovery`](../evidence/wo12-capital-recovery/README.md). The four committed lifecycle transactions each paid 2,000 shannons. Dry-run cycles were 1,874,169 (payment), 1,822,632 (close), 1,662,203 (late deposit), and 1,732,132 (late sweep), as reported by CKB 0.210.0. Rejected cases were checked by `send_transaction` and failed in `Inputs[0].Type`; this experiment does not claim cycles for rejected transactions.

This is meaningful capacity recovery for a small treasury relative to Q's own 600 CKB allocation: 77.7% is returned, with a 22.3% permanent residual. It may matter for operators that create and close many treasuries, but 134 CKB per closed treasury still accumulates. Fees are small in the tested local setup, while user-perceived economics depend on CKB value, external fee inputs and the shared cost of publishing the v2 executable. No operator was interviewed, and no demand or product-market fit is established.

## Product Direction

The strongest concrete job found is the CKB Community Fund DAO V1.1 project execution wallet, but none of the candidates shows demand for QuotaCell or that existing tools are inadequate.

[ChainPay](https://github.com/toastmanAu/chain-pay) already describes payroll, invoice ingestion, multisig co-signing and confirmed CKB payment reconciliation, so QuotaCell should not rebuild payroll. [Remit](https://github.com/Ticoworld/remit) is an application-level action runtime whose policy is currently off-chain; an optional enforcement adapter is a possible integration boundary. [Sluice](https://talk.nervos.org/t/introducing-sluice-a-liquidity-operations-workspace-for-ckb-fiber/10532) handles Fiber liquidity and route operations, not treasury spending. [ckb-session-kit](https://www.npmjs.com/package/ckb-session-kit) already scopes an individual session key. These projects establish adjacent or overlapping work, not customer demand.

The product should remain a spending-control primitive, not become Remit, Sluice, NERVE, ChainPay or a general agent wallet. Policy-state contention remains: each delegate transition consumes the same single Q cell. Native CKB is a separate ABI/asset path; it cannot be claimed from this xUDT experiment. An ordinary owner would need the product UI to explain that close returns 466 CKB, leaves 134 CKB locked permanently, and late F deposits remain recoverable only with the owner key.

## Decision and Next Work

Advance the v2 compact CLOSED successor to broader adversarial and regression qualification. Keep v1 and its published evidence untouched. Do not change existing F lock args or imply migration: v1's exact Q Script hash is embedded in F args, Qv1 requires the fixed state/capacity successor, and its immutable validator cannot accept the smaller v2 state. A v1 owner can recover through v1 and then create a separate v2 treasury; that is a two-step re-funding workflow, not in-place migration.

The next architecture experiment should compare compact-v2 against a purpose-built Fv2 owner-only recovery threshold. Implement neither until a checker demonstrates that pre-threshold spends always consume current Q, post-threshold spends require owner K, late post-retirement F cells inherit the same threshold, and Q deletion cannot strand any supported cell. Measure the extra F occupied capacity and node fees. Do not add a general multisig replacement, arbitrary asset adapter, time-based rule copied from CrowdCell, or broad payment workflow.
