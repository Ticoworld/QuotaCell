### WO15E submission timeout follow-up

Fresh read-only checks against `https://testnet.ckb.dev/` and `https://testnet.ckbapp.dev/` both returned `unknown` for `0x21bffcfec131070fa7de3158543e30d05bdb6cc9885144b4124da6dc1a2a29f4` and `live` for its original input `0x3fa9dd0155936e0dacc9bf5e57a4785c3d6d66191a7560f1ff5ec6a6b04954f3:2`. The local deployment journal was empty. The old implementation writes its first journal entry immediately before sending, so the empty journal indicates the tool did not reach its send call; the original signed bytes had nevertheless been sent to the dry-run RPC, and unknown responses do not prove they can never be relayed. No resend or replacement was made.

The exact timed-out RPC cannot be identified retrospectively: the previous server logged no method or phase. Its 15-second per-call limit applied during network, dependency, funding, fee and dry-run checks. A subsequent read-only diagnostic observed all sampled calls succeeding, including the 1 MiB K data read; it cannot establish which earlier call failed.

The submission path now labels the failing pre-submission phase and RPC method, including a public outpoint for live-cell calls, while retaining the 15-second bound. A failure before the journal/send boundary preserves the signed ticket in memory until its existing expiry for a further explicitly requested manual action; it performs no automatic send or retry. Once journaling begins, the ticket is consumed and cannot be reused, preserving conservative handling of uncertain outcomes. The UI distinguishes a known pre-submission failure from an uncertain send. Controlled tests cover timeout in network, dependencies, input, fee and dry-run stages, explicit recovery using the same in-memory ticket, and no retry after attempted sends; existing cryptographic verification and server routing tests passed. One test server initially failed its readiness deadline and passed when rerun.

The original server had already cleared its in-memory ticket on the timeout, and signed bytes were deliberately not stored on disk. They cannot be recovered from the journal or the verification record. A further wallet approval would therefore be needed for a newly prepared transaction if the original hash is conclusively resolved and the user chooses to continue. The running server has not been restarted or switched to the updated code during the uncertain outcome.
